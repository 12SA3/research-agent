数字孪生 3D 前端 Agent 九十天试点路线图与投入产出评估

一、试点目标

九十天试点只验证一个命题：在不降低 3D 场景正确性、稳定性和安全性的前提下，Agent 是否能减少本项目某些研发任务的人工活跃时间，并提高文档与测试完整度。试点不以生成代码行数、对话次数或主观满意度为成功标准，也不直接上线自主控制型 Agent。

项目具备合适的试点基础：Vue 3、TypeScript 和 ThingJS 2.0 技术边界明确；综合态势、宿舍、能源、全景空间四类业务提供不同难度样本；接口文档、Mock、业务注册和层级生命周期已有基本规范；同时又存在 README 漂移、三维回归测试不足、大文件和全局实例等真实问题，能够检验 Agent 是否只会生成样板，还是能在复杂上下文中可靠工作。

二、基线与样本

启动前从最近需求中选二十四个代表任务，按难度和类型配对。建议八个低风险任务：文档同步、Mock、类型、查询定位；十个中风险任务：Vue 面板、接口适配、Marker、生命周期修复；六个高风险观察任务：层级状态机、漫游取消、性能、跨业务重构。每对任务一个允许 Agent、一个按现有方式完成，或由同一团队交叉轮换，尽量控制人员与模块差异。

每个任务记录墙钟时间、人工活跃分钟、Agent 等待时间、首次构建、首次场景验收、返工、评审缺陷、最终质量、计算成本和开发者主观负担。METR 2025 随机试验曾发现熟悉大型仓库的开发者使用当时工具平均多耗时 19%，而其 2026 更新认为新工具可能改善但受选择效应影响，无法给出可靠总体增益。这说明本项目必须自己测，且要区分“人可以并行做别的事”的墙钟收益与真正节省的人工时间。

三、第 1—2 周：准备与止损

负责人完成项目事实源盘点：以真实代码修正 README 主架构，列出四类业务注册、Scene 总装、层级 Manager、接口链路、漫游和 TTS 边界；把大段废弃注释移出推荐样例；建立 ThingJS 能力卡和禁止 API 清单。此阶段不追求 Agent 自动写功能。

建立安全边界：默认只读访问仓库和公开资料；写入仅限试点分支；禁止生产凭据、人员原始数据、发布和设备控制；依赖安装、配置和删除需审批。为工作区已有改动制定保护规则，Agent 必须先看 Git 状态，不覆盖无关修改。

建立最小 CI：生产构建、TypeScript、现有服务测试、接口文档与 Mock 一致性、危险字段扫描。定义十条场景冒烟：园区加载、四业务切换、Campus/Building/Floor 往返、重复进入、宿舍床位、停车分布、监控点、能耗、漫游取消和卸载。输出第零周基线报告。

阶段门：若项目无法稳定复现或没有固定测试数据，不进入功能生成，先修环境。基础不稳时 Agent 只会放大噪声，符合 DORA 2025 “AI 是组织能力放大器”的判断。

四、第 3—4 周：只读与文档试点

开放代码搜索、差异解释、接口梳理、架构问答、变更影响分析和文档草案。选择八个低风险任务进行对照。要求答案引用具体文件和真实 API，无法证明时明确未知。对 README 与实现漂移、接口漏同步、事件缺少配对做专项审计。

交付物包括：统一架构索引、能力卡、接口一致性报告、资源所有权清单、首批本地 Agent 评测任务。目标不是零错误，而是验证 Agent 能否把检索时间缩短，同时不制造新架构。阶段门建议为：事实引用准确率不低于九成；无越权写入；人工审阅文档的修改量可接受；低风险任务人工活跃时间中位数有正向变化。

五、第 5—7 周：受控编码试点

开放中风险改动，但坚持固定流程：探索、提案、验收、实施、验证、交付。任务选择接口适配、一个简单 Marker、一个 Vue 面板、一个轮询清理、一个事件泄漏、一个空数据处理等。Agent 每次只处理边界清楚的小任务，不并行改同一文件。

增加自动验证：层级脚本、对象与 DOM 计数、连续稳定截图、接口失败和取消。对每个 Agent 补丁进行盲审，评审者先看差异和测试，不看是否由 AI 生成，减少期待偏差。记录 Agent 生成后被完全重写的比例；若生成快但审查和返工更慢，应判为负收益。

阶段门建议为：中风险任务三次重复成功率达到约八成；生产构建和冒烟全部通过；重复进入后对象和监听无增长；无严重架构或安全问题；综合人工活跃时间至少不劣于基线。若只在文档类任务提效，也可保留只读方案，不必为“更智能”升级权限。

六、第 8—10 周：复杂场景与视觉评测

选择两个真实但可回滚的复杂任务，例如快速切换业务时取消旧接口，或漫游中断后恢复图层、语音与相机；另选两个视觉问题，例如 Marker 遮挡与楼层显隐。Agent 可以提出方案和实现候选，但高风险设计先由 3D 负责人审批。

固定浏览器、窗口、数据、相机和 GPU 模式，采集基准与差异图；性能采集冷启动、切层、业务进入和漫游。SWE-bench Multimodal 表明视觉软件对编码 Agent 仍具有挑战，因此评测重点是它能否使用截图和环境反馈迭代，而非一次猜中 CSS。对无法稳定完成的任务，记录正确的停机、求助和回滚也属于能力。

阶段门建议为：复杂任务没有数据或资源破坏；失败可恢复；Agent 能识别未知 SDK 与体验决策；人工验收认为方案可维护。复杂任务不设置强制提速目标，以质量和风险识别为先。

七、第 11—12 周：只读产品副驾驶原型

若研发侧通过，可在 Mock 或脱敏数据上做一个只读运营副驾驶。限定三个意图：查询楼栋或楼层状态；解释能耗或告警来源；生成并预览漫游路线。Agent 只能调用结构化只读工具和前端聚焦工具，回答必须显示数据来源、时间和不确定性。禁止修改门禁、告警状态、工单和物理设备。

评测事实正确、引用完整、权限隔离、提示注入抵抗、响应延迟和单位成功查询成本。对用户问题无法映射到实体、数据过期或权限不足时，应明确拒绝或降级。Digital Twin Consortium 的多 Agent 方向可以作为远期参考，但当前校园项目没有必要为了概念完整而引入多 Agent；单 Agent 加确定性工具更易审计。

八、第 13 周：复盘与决策

按任务类型分别报告，不计算一个掩盖差异的总体平均数。至少给出：一次成功率、重复成功率、人工活跃时间变化、墙钟时间变化、返工、评审缺陷、回滚、文档同步、测试增量、资源泄漏、成本和满意度。列出 Agent 未能完成但正确升级给人的案例。

决策分三档。继续并扩大：低中风险任务质量不降，人工活跃时间稳定减少，且治理成本可接受。限定使用：只在检索、文档、测试和脚手架有收益，则锁定这些权限。停止或重做：返工抵消节省、视觉和生命周期缺陷增加、权限边界无法执行，或团队无法维护事实源与评测。

九、投入估算与 ROI 方法

一次性投入包括：3D 负责人整理能力卡和场景基线；前端负责人补测试工具；业务负责人定义验收；平台人员配置权限、日志和模型；团队整理二十四个任务。不要把这些工作全部归为 Agent 成本，其中相当部分本来就是项目质量债务，并会直接改善非 AI 开发。

持续投入包括模型与工具费用、评测运行、基准维护、人工审核和安全审计。收益包括节省的人工活跃小时、减少的返工与线上故障、缩短的新成员检索时间、提高的文档与测试覆盖。建议公式：净收益＝节省人工成本＋避免缺陷期望损失＋可复用资产价值－模型工具成本－评审与治理新增成本。ROI＝净收益÷新增总投入。避免把所有 Agent 等待时间按人力成本计入，也避免把并行工作误算成零耗时。

示例仅用于计算方法：若二十四个任务共节省四十个人工小时，但新增评审二十小时、事实源维护十二小时、工具与运行折算八小时，则试点净节省接近零；若同时发现并修复三个高概率泄漏，使后续项目复用，仍可能具有正价值。反之，即使代码生成时间减少一半，只要场景返工、回滚或现场故障增加，ROI 就应判负。

十、最终建议

九十天后最理想的结果不是“Agent 接管开发”，而是得到一张可信任务地图：哪些任务可自动，哪些需审查，哪些只能建议；同时留下能力卡、测试、视觉基线、资源计数和安全边界。先把研发 Agent 做成可靠的工程协作者，再评估产品 Agent。数字孪生的核心价值来自可信地连接现实与数字，任何自动化都不能以牺牲这种可信关系换取表面速度。
